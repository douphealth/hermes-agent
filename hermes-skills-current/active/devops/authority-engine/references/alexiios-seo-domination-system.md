# Alexiios SEO Domination System

## Overview

This is the master workflow for Alexiios's websites when the mission is aggressive organic growth: higher SERP rankings, stronger topical/entity authority, better AI Overview / LLM citation visibility, more answer-box capture, better monetization, and compounding traffic across WordPress properties.

The goal is not generic SEO activity. The goal is a verified execution loop that finds commercial demand, maps real SERP competitors, builds entity-rich topical authority, improves answer extraction, strengthens trust, ships live WordPress upgrades, and measures results.

Important: never promise guaranteed #1 rankings. Instead, execute the highest-probability path to outperform competitors using technical SEO, content architecture, entity coverage, SERP modeling, internal links, trust, schema, and monetization assets.

## Operating Principles

1. **Execution over theory** — do not produce a long strategy if REST execution can ship improvements now.
2. **Revenue-first SEO** — prioritize commercial value, affiliate intent, lead capture, and conversion paths over vanity traffic.
3. **SERP reality beats keyword imagination** — use live SERPs / competitor overlap wherever possible.
4. **Entities beat keyword stuffing** — build entity graphs, topical relationships, attributes, comparisons, and explicit definitions.
5. **AEO/GEO extraction matters** — every important page should have self-contained answer blocks, definitions, tables, FAQs, steps, summaries, and schema-ready structure.
6. **AI visibility is earned by clarity and trust** — citeable claims, stable entities, author/trust proof, structured answers, and unique information gain.
7. **Internal links create authority flow** — every money page needs parent, child, sibling, and trust links.
8. **Technical indexability is non-negotiable** — 200 OK, canonical accuracy, sitemap coverage, robots index/follow, clean H1, metadata, schema, crawlable links.
9. **Preserve design unless asked to redesign** — use additive premium blocks and body-layer upgrades.
10. **Verify live** — after changes, fetch public URLs and confirm output.

## Full Workflow

### Phase 0 — Site Selection and Access

If the user names a site, execute on that site.
If the user says all websites, build a portfolio queue and start with the site/page cluster with the highest expected ROI.

Before editing:

- retrieve REST credentials from the secrets file only when needed
- confirm REST auth works
- confirm target page/post IDs
- avoid wp-admin because Cloudflare often blocks it
- prefer REST, direct POST, or server/API paths

### Phase 1 — Technical SEO Baseline

For each site or priority page, verify:

- HTTP status is 200
- canonical is self-referencing or intentionally consolidated
- robots meta allows index/follow
- included in XML sitemap or auxiliary sitemap
- exactly one H1
- title and meta description exist and match intent
- schema exists and is not misleading
- internal links are crawlable HTML links
- no obvious duplicate slug/permalink collision
- no noindex, redirect loop, soft 404, blocked robots.txt path, or canonical mismatch

P0 blockers must be fixed before content scaling.

### Phase 2 — Keyword + Entity Research

Build a demand map, not a flat keyword list.

For each niche/site:

1. Identify commercial head terms.
2. Expand into query ladders:
   - best / top / review
   - vs / alternatives / comparison
   - cost / price / worth it
   - problem / mistake / risk
   - how to / guide / checklist
   - symptoms / causes / prevention
   - tools / products / services
   - audience modifiers
   - geography modifiers if relevant
3. Extract entity sets:
   - core entities
   - attributes
   - problems
   - solutions
   - products/tools
   - brands/competitors
   - methods/processes
   - measurements/criteria
   - risks/contraindications
   - related subtopics
4. Map each entity to pages:
   - existing page that should own it
   - missing page that should be created
   - supporting section within a hub
   - FAQ/answer block opportunity

Output should include:

- primary keyword
- secondary keywords
- entities to cover
- search intent
- page type
- monetization path
- internal-link targets
- AEO/GEO extraction targets

### Phase 3 — SERP and Competitor Research

Use SERP-overlap discovery, not guessed competitors.

For each query bucket:

- collect top ranking domains/URLs
- normalize domains
- score repeated competitors by appearances, average position, and high-intent coverage
- identify hidden competitors
- identify winning page types
- identify snippet/PAA/AI Overview surfaces
- identify trust and UX patterns
- identify content gaps and information-gain angles

Competitor mining must answer:

- Who is actually winning across the query set?
- What page type is Google rewarding?
- What are they doing structurally that the target site lacks?
- Where are they weak, outdated, generic, thin, unsourced, or under-monetized?
- What can Alexiios publish or upgrade that is clearly more useful?

### Phase 4 — Opportunity Scoring

Score every opportunity from 0-100 using:

- Commercial value: 0-20
- Ranking feasibility: 0-15
- Existing authority fit: 0-15
- SERP weakness: 0-15
- AEO/GEO/snippet upside: 0-10
- Internal-link leverage: 0-10
- Monetization clarity: 0-10
- Production speed: 0-5

Prioritize:

1. Technical/indexability blockers on money pages.
2. Pages already ranking positions 4-20 with high commercial value.
3. Commercial hubs and comparison pages.
4. High-AEO informational pages that can feed money pages.
5. Entity gaps needed to complete topical authority.

### Phase 5 — Page/Cluster Architecture

Every serious cluster should include:

- one commercial hub or money page
- supporting informational guides
- comparison/alternatives pages where relevant
- FAQ/PAA support pages or sections
- trust/methodology/disclosure support
- internal-link map
- conversion asset

Internal-link rules:

- hub links to all child pages
- child pages link back to hub
- sibling pages link where intent overlaps
- informational pages link to commercial next step
- money pages link to trust/proof pages
- all links use descriptive, non-spammy anchors

### Phase 6 — Content Upgrade Standard

Each upgraded or new page should include:

- answer-first opening
- clear H1 matching intent
- concise table of contents where useful
- entity-rich section stack
- comparison tables where commercial
- pros/cons or decision criteria where useful
- specific examples and practical steps
- trust/proof block
- author/editorial or methodology notes where relevant
- FAQ section for PAA/AEO
- schema-compatible structure
- strong CTA or monetization path
- related internal links
- freshness/update note when relevant

Avoid:

- generic AI filler
- keyword stuffing
- fake claims or invented statistics
- unverifiable medical/financial claims
- copying competitor headings blindly
- publishing informational content with no next step

### Phase 7 — GEO / AI Visibility Optimization

For AI Overview, Perplexity, Gemini, ChatGPT/Bing-style answer engines, and LLM citation likelihood, add:

- short direct answer blocks under key questions
- definition blocks for core entities
- tables that compare options/criteria
- step lists for how-to queries
- concise summaries that can be quoted independently
- explicit entity relationships: X is used for Y, differs from Z, risks include A/B/C
- cited or clearly attributed claims when statistics/medical/scientific facts appear
- updated date and freshness signals
- author/trust context
- schema where appropriate

Every priority page should contain at least one extractable asset:

- paragraph answer
- list answer
- table answer
- FAQ answer
- decision framework
- checklist

### Phase 8 — Monetization Optimization

For commercial pages:

- place CTA above the fold where natural
- add comparison tables
- add buyer-intent sections
- add best-for / use-case segmentation
- add affiliate disclosure where needed
- add trust blocks before CTAs
- link informational pages into commercial next steps
- include newsletter/lead capture if relevant
- make the next click obvious

Never sacrifice trust for aggressive monetization. Trust increases rankings and conversion.

### Phase 9 — WordPress REST Execution

For Alexiios's sites:

- use REST credentials from the local secrets file
- fetch current page/post content first
- preserve design unless redesign requested
- use additive HTML blocks wrapped as needed
- avoid breaking shortcodes and theme blocks
- update metadata through available REST/meta mechanisms
- purge cache if available
- verify public HTML after publishing

Verification per changed URL:

- public page returns 200
- visible content appears
- canonical is correct
- robots index/follow
- H1 count is sane
- internal links render
- schema/FAQ blocks are valid or at least structurally clean
- no obvious layout break

### Phase 10 — Measurement and Refresh Loop

After execution, record:

- changed URLs
- target keywords/entities
- cluster relationships
- monetization path
- expected ranking movement window
- what to check next

Refresh cadence:

- high-value money pages: monthly
- pages in positions 4-20: every 2-4 weeks until improved
- evergreen support pages: quarterly
- volatile/news/product pages: as SERP changes

## Common Pitfalls

1. **Doing research without shipping.** If a safe edit can be made, ship it.
2. **Chasing high-volume informational keywords with no monetization path.** Prioritize revenue and authority leverage.
3. **Ignoring technical blockers.** Canonical/noindex/sitemap/H1 issues can erase content gains.
4. **Treating GEO/AEO as separate from SEO.** Extraction-ready blocks should be built into every priority page.
5. **Over-redesigning.** Preserve existing design unless the user explicitly asks for redesign.
6. **Guessing competitors.** Use SERP overlap.
7. **Creating duplicate pages.** Map existing content before publishing new URLs.
8. **Overpromising #1 rankings.** Execute the strongest path; rankings are probabilistic and externally controlled.
9. **Publishing unsourced claims.** Especially in health, pets, finance, or product review contexts.
10. **Forgetting cache/CDN verification.** Always verify public HTML, not just REST response.
