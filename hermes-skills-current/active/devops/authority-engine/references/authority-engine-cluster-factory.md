# Authority Engine Cluster Factory

Use this when the user wants to turn a topic, category, or commercial territory into a full cluster system rather than isolated pages.

This is the system for:
- pillar/cluster architecture
- parent/child page maps
- support-page generation plans
- hub/category alignment
- internal-link blueprints
- rollout sequencing for topical territories

## Mission
Turn one promising topic into a compounding topical territory with clear hubs, support pages, authority flow, and rollout order.

## Core principles
1. Clusters should be designed around intent and authority flow, not just keyword lists.
2. Pillars need support pages that remove ranking friction.
3. A cluster should route users and authority, not just exist as a content inventory.
4. Fewer stronger clusters beat random sprawl.
5. Each support page must have a distinct job.
6. The cluster should define its own refresh and expansion logic.

## Cluster model
A strong cluster usually includes:
- 1 pillar / hub page
- 2–5 money or near-money pages
- 3–10 support pages
- 1–3 trust/supporting infrastructure pages where relevant
- defined internal-link routes
- defined next-step CTAs
- freshness ownership

## Standard workflow

### Phase 1 — territory definition
Define:
- core topic or commercial territory
- target audience
- buyer stage mix
- dominant monetization path
- whether the territory is informational, commercial, or hybrid

### Phase 2 — intent segmentation
Break the territory into page classes:
- pillar / hub
- money pages
- comparison / alternatives pages
- use-case pages
- how-to / support pages
- FAQ / glossary / definition pages
- trust-support pages if the topic is sensitive or commercial

### Phase 3 — hub and taxonomy choice
Decide:
- which page is the main hub
- whether a category/hub page should be created or upgraded
- which pages are children vs siblings
- which pages should not exist because they would cannibalize nearby pages

### Phase 4 — support-page design
For each support page, define:
- exact job in the cluster
- target query class
- relation to the pillar or money page
- which objections / subquestions / modifiers it resolves
- what internal links it must contain
- what CTA or next-step it should route to

### Phase 5 — internal-link blueprint
Map:
- pillar -> all core children
- support pages -> pillar
- sibling links where relevance is high
- money pages -> trust pages
- support pages -> next-step conversion pages where appropriate
- inbound links from older strong pages into the new/weak cluster pages

### Phase 6 — rollout sequencing
Deploy in this order by default:
1. main hub / pillar
2. top money pages
3. highest-leverage support pages
4. trust/supporting pages if needed
5. remaining support pages
6. internal-link normalization across the cluster

### Phase 7 — expansion logic
Define how the cluster grows after first release:
- which modifiers are not covered yet
- which support questions remain open
- which pages need second-wave upgrades
- which pages should be refreshed first if KPIs move

## Cluster page roles
Every page in a cluster should have one main role:
- define
- compare
- persuade
- troubleshoot
- qualify
- route
- convert

If a page has no clear role, it should probably not exist.

## Output contract
Report:
- territory chosen
- pillar/hub page
- member pages by role
- support-page plan
- internal-link blueprint
- rollout order
- expansion / second-wave opportunities

## Quality bar
A good cluster factory should make the topic feel inevitable: the user should see exactly what pages exist, why they exist, how they connect, and what to build next. If it produces a messy keyword pile, it failed.
