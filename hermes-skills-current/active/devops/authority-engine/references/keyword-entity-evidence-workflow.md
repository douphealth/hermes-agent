# Keyword + Entity Evidence Workflow

Use this when Alexiios asks for the best, most semantically relevant keywords/entities for every blog post, landing page, rewrite, or topical authority pass.

## Non-negotiable standard
Do not finalize a page brief, rewrite, or published article from model intuition alone. Build a concise evidence-backed keyword/entity map first, then weave it naturally into headings, answer blocks, body copy, FAQs, schema, internal anchors, image alt/captions, and CTA-adjacent copy where it genuinely fits.

## Preferred evidence hierarchy
1. First-party data: Google Search Console queries/pages, site search logs, existing WordPress analytics, conversion/query data.
2. Google demand sources: Google Keyword Planner, Google Trends, live Google SERP, People Also Ask, autocomplete, related searches.
3. High-trust SEO datasets when available: Ahrefs, Semrush, Moz, LowFruits, AlsoAsked, Screaming Frog exports, Search Console exports.
4. Competitive SERP evidence: pages repeatedly ranking across the head term, mid-tail variants, comparison queries, and problem/solution modifiers.
5. Entity extraction and schema evidence: ranking-page schema, Wikipedia/Wikidata/Knowledge Graph-style named entities, product/category entities, attributes, subtopics, measurements, risks, benefits, and adjacent concepts.

## Execution pattern
1. Define the dominant intent and page type before researching: informational, commercial investigation, transactional, local, troubleshooting, comparison, app/tool landing page, or hub.
2. Pull candidate queries/entities from at least two evidence classes above whenever access exists. If Google Keyword Planner/Trends are unavailable, state the exact substitute evidence used instead of implying Google validation.
3. Group findings into:
   - primary keyword
   - secondary variants
   - long-tail/PAA questions
   - semantic entities and attributes
   - product/category entities
   - trust/evidence terms
   - internal-link anchor opportunities
   - FAQ/schema candidates
4. Filter aggressively: keep only terms that match intent and can be used naturally. Drop awkward, off-intent, or spammy variants.
5. Map terms to placements: H1/title direction, H2/H3s, direct-answer paragraphs, body sections, checklist/table labels, FAQ questions, schema, alt/captions, internal anchor text.
6. Write or rewrite in natural language. The finished page must read like expert editorial content, not a visible keyword/entity dump.
7. Verify before publishing/reporting: no raw keyword lists leaked into public copy unless explicitly designed as a useful checklist/glossary; no invented search volumes/trends; one clear H1; schema remains valid; internal links and CTA routes work.

## Pitfalls
- Never claim Keyword Planner, Google Trends, GSC, Ahrefs, or Semrush were used unless the tool/export was actually accessed.
- If premium keyword tools are unavailable, keep momentum: use live Google/autocomplete/SERP-style evidence where accessible, the target app/page copy, sitemap/internal-link inventory, reputable public sources, competitor pages, and schema/entity extraction. Report the substitute evidence used rather than blocking execution.
- Do not publish internal GSC/Bing metrics visibly on WordPress pages.
- Do not force every entity into the page; coverage must improve topical completeness and user usefulness.
- Avoid naked entity strings such as comma-separated keyword dumps, “reader intent map,” or AI-scaffold labels in public content.
- For health, fitness, pet, nutrition, or pest/YMYL-adjacent pages, include entities naturally but add safety language and authoritative-source context; do not turn keyword coverage into unsafe medical/veterinary claims.
- For affiliate/content monetization pages, keyword relevance is not enough: verify contextual relevance and accurate final affiliate/deep links before inserting commercial links.
