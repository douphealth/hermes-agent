# WordPress Imported Rewrite Layout Recovery

Use this when a rewritten/imported WordPress post publishes successfully but the user reports the live blog post is visually distorted, duplicated, or unreadable.

## Core lesson

Do not mix rendered public HTML or old post body fragments back into a clean rewrite. Old TOC output, review widgets, Elementor/Kadence wrappers, affiliate boxes, and plugin-rendered shortcodes can contaminate the new body and create duplicate hero blocks, purple/legacy template sections, oversized images, and inconsistent widths. Rebuild from the clean source file, then reinsert only the minimum verified monetization modules.

## Fast recovery sequence

1. **Immediately inspect rendered layout**
   - Open the live canonical or cache-busted URL in the browser.
   - Use visual inspection for oversized hero images, duplicate intros, plugin TOC/review modules, fixed-width tables, and legacy/editorial brief sections.
   - Run a DOM overflow probe:
     ```js
     (() => {
       const w = window.innerWidth;
       const bad = [];
       document.querySelectorAll('body *').forEach(el => {
         const r = el.getBoundingClientRect();
         const cs = getComputedStyle(el);
         if (r.width > w + 8 && cs.display !== 'none') {
           bad.push({tag: el.tagName, cls: String(el.className).slice(0,80), w: Math.round(r.width), left: Math.round(r.left), text: (el.innerText || '').slice(0,80)});
         }
       });
       return {vw: w, docScroll: document.documentElement.scrollWidth, bodyScroll: document.body.scrollWidth, bad: bad.slice(0,12), h1s: [...document.querySelectorAll('h1')].map(h => h.innerText.trim())};
     })()
     ```

2. **Rebuild from clean source**
   - Start from the original rewrite file or backed-up clean HTML, not from the currently rendered public page.
   - Strip package comments and internal implementation sections.
   - Do **not** append old rendered content that contains plugin TOC markup (`ez-toc-*`), duplicate headings/anchors, old comparison sections, or previous template modules.
   - Demote any body `<h1>` when the theme already prints the post title.

3. **Reinsert monetization narrowly**
   - Add a simple, scoped affiliate CTA box only when a verified offer exists.
   - Preserve standard attributes: `rel="sponsored nofollow noopener"`, `data-amfs-offer`, `data-amfs-position`, and page ID metadata.
   - If no verified affiliate URL exists for the primary product, use the official direct link and label it as non-affiliate; do not invent a tracking URL.

4. **Add emergency scoped CSS if layout is already broken**
   - Scope to the post/body module, not global sitewide CSS.
   - Constrain featured images and media: `max-width:100%; height:auto; object-fit:contain`.
   - Prevent horizontal overflow on article wrappers.
   - Wrap tables with horizontal scroll and set mobile button/card behavior.
   - Avoid changing theme/global layouts unless the distortion is global.

5. **Publish via XML-RPC when style tags are needed**
   - REST may strip `<style>` and `@media`; XML-RPC preserves them.
   - Always back up the current post body before overwriting.

6. **Purge and verify**
   - Purge the exact Cloudflare URL if token is available.
   - Recheck both canonical and cache-busted URLs.
   - Verify: HTTP 200, one H1, no old legacy markers, no overflowing elements, clean image constraints, affiliate CTA metadata, schema parses, and rendered desktop/mobile readability.

## Bad markers to search for after rebuild

- `ez-toc-title`, `ez-toc-section`, or old generated anchor IDs from a previous article.
- Duplicated product-review headings such as old pricing/version sections that are not in the clean rewrite.
- Internal production sections: `Search-Intent Brief`, `Content Quality Gate`, `Implementation checklist`, `Recommended Internal Links` when not intended for readers.
- Duplicate hero image/title blocks.
- Multiple visible affiliate disclosures generated by different templates.

## Reporting style for this user

If the user says the post is distorted, treat it as an emergency repair. Do not over-explain before acting. Final report should be short and evidence-based: what was removed, what was constrained, purge status, H1 count, overflow count, and screenshot/path if available.
